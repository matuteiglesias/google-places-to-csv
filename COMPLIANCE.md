# Provider data and compliance boundary

This project is a governed API client and local-business discovery kernel. It does **not** grant rights to store, redistribute, sell, or use provider content beyond the rights granted by each provider's current terms.

Provider policy metadata in the codebase is dated operational guidance, not legal advice. Re-verify provider terms before material production use.

## Google Places

Policy metadata last verified: **2026-09-07**.

Authoritative references:

- Places API policies: https://developers.google.com/maps/documentation/places/web-service/policies
- Place IDs: https://developers.google.com/maps/documentation/places/web-service/place-id
- Google Maps Platform terms: https://cloud.google.com/maps-platform/terms
- Maps service-specific terms: https://cloud.google.com/maps-platform/terms/maps-service-terms

Current practical boundary represented by this repository:

- Current service-specific terms permit caching Google ID values such as Places `place_id` where the applicable documentation allows it.
- Google Maps Platform terms restrict exporting, extracting, bulk-downloading, copying, or saving Google Maps/Places content outside the Services except where expressly permitted.
- Other Google Places content remains subject to the current Google Maps Platform terms, including applicable caching/storage/redistribution restrictions.
- EEA customers may be governed by different Google Maps Platform terms and functionality.
- The `refs` output contract intentionally contains only the provider key, Google Place ID, and provenance generated by this client (`source_query`, `observed_at`).
- `business` and legacy `provider` outputs are **provider-terms-controlled**. The existence of CSV/JSON output must not be interpreted as permission to retain, redistribute, or turn Google Places content into a permanent prospect database.

For durable cross-provider workflows, prefer a provider whose own contract explicitly covers the intended persistence/use rather than treating a Google Places response as a permanent lead database.

## Openmart

Policy/product metadata last verified: **2026-09-07**.

Current public references:

- API tutorial: https://www.openmart.com/product-tutorials/using-the-openmart-api-to-fetch-data
- Local Business Data API: https://www.openmart.com/products/local-business-data-api
- API docs entry point: https://api.openmart.ai/docs

Openmart's current public product documentation explicitly markets its Local Business API for B2B lead generation and states that returned structured JSON may be stored and used. The repository therefore marks the adapter as `provider-documented-lead-generation` rather than inheriting Google's persistence restrictions.

This is still not a legal guarantee. Before production use, verify the terms attached to the actual Openmart account/subscription and any jurisdiction-specific marketing/privacy obligations relevant to downstream outreach.

The Openmart adapter intentionally stops at business discovery/normalization. It does not automatically enrich people, unlock paid contact fields, or perform outreach.

## Provider contract

Every provider adapter added to the kernel must declare a `ProviderSpec` containing at least:

- provider key and display name;
- authoritative documentation URL;
- terms/policy URL or best available current provider policy surface;
- policy verification date;
- persistence mode and human-readable persistence summary;
- durable identifier;
- supported capabilities.

An adapter must not inherit another provider's persistence assumptions. Persistence and redistribution rules are provider-specific contracts.

Candidate future providers include Foursquare Places and Geoapify. Their presence in planning documentation is not a certification of their legal/commercial terms and does not mean an adapter is implemented.

## Cost and policy are separate contracts

Google field/SKU classification lives in `gmaps_scraper/billing.py`. Provider persistence policy lives in `gmaps_scraper/providers.py` and this document.

Do not collapse them. A cheap field is not automatically persistable, and a persistable provider record is not automatically cheap.

## Credentials and paid usage

- Never commit provider credentials.
- Use provider-specific environment variables or secret stores.
- Restrict API keys according to the provider's security guidance.
- Normal CI is credential-free and must remain incapable of making paid provider calls.
- Multi-cell censuses must preflight request/record budgets before network calls.
- Provider-specific paid enrichment beyond the normalized business record is outside the default census workflow.
